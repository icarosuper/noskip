# Schema change

The schema lives in `src/db/schema/` (re-exported from `index.ts`); migrations in `drizzle/` are
generated by drizzle-kit and committed with the change. Read
[architecture.md](../../../docs/agents/architecture.md) "Data model" first — it says which tables
are catalog (importer-only) and which are ours.

## 0. Know which kind of table you are touching

| Table | Written by | Extra work |
|---|---|---|
| `anime`, `theme`, `song`, `artist`, `song_artist` (`catalog.ts`) | **only** `scripts/import/` | importer + its tests, fixture catalog, maybe [data-sources.md](../../../docs/agents/data-sources.md) |
| `user`, `session`, `account`, `verification` (`auth.ts`) | Better Auth | **generated** — never hand-edit, step 1b |
| `rating`, `review`, `review_report`, `favorite`, `profile`, `follow` | the app | server functions, fixtures, demo seed |

Hard rules ([decisions.md #1](../../../docs/agents/decisions.md#1-the-catalog-is-a-local-copy-of-animethemes-upserted-never-deleted)):
ratings point at `theme.id`, so a migration must **never** delete catalog rows, drop `theme`, or
change `theme.id`/`animethemes_id` in a way that loses the link. A destructive change to a table
with user data (drop column, narrow a type, new `NOT NULL` without default) needs the user's OK
first — say what would be lost.

## 1a. Edit the schema

Edit `src/db/schema/<file>.ts`. A new file also goes into `index.ts`. Constraints the code relies
on belong in the database (`check(...)`, `unique`, composite FKs — see `ratings.ts`), not only in
zod.

## 1b. Auth tables: regenerate, don't edit

Change `src/lib/auth.ts` / `src/lib/auth-options.ts` (plugins, `additionalFields`), then run the
command in the header of `src/db/schema/auth.ts`:

```bash
bunx --bun auth@latest generate --config src/lib/auth.ts --output src/db/schema/auth.ts
```

It writes with its own formatting (double quotes, semicolons); Biome ignores the file, so leave it.

## 2. Generate the migration and read it

```bash
bun run db:generate --name <what-changed>     # kebab-case: theme-season, profile-avatar
```

- **If drizzle-kit asks "create or rename?"** it needs a TTY and can't be answered here. Stop and
  ask the user to run it themselves with `! bun run db:generate --name <name>` and pick the answer
  (a rename keeps the data; create+drop loses it).
- **Read the new `drizzle/NNNN_<name>.sql`** before applying. Look for: `DROP` you didn't intend,
  `NOT NULL` added to a table with rows and no default (fails on migrate), a rename turned into
  drop+add, a type change that truncates. Fix the schema and regenerate — never edit the SQL or
  `drizzle/meta/` by hand, and never delete an applied migration.
- Data that must be backfilled (e.g. a new column computed from existing rows): ask the user how;
  it is either a custom migration (`bunx drizzle-kit generate --custom --name <name>`, SQL written
  by hand in the empty file it creates) or an importer re-run for catalog columns.

## 3. Apply

```bash
bun run db:migrate        # the dev database (DATABASE_URL in .env.local)
```

Never `db:push` against a database with data. The test databases migrate themselves:
`noskip_test` in the Vitest global setup, `noskip_e2e` on every `e2e:prepare` / `e2e:server`.

## 4. Carry it through

Go down the list; skip what doesn't apply, but decide each one consciously:

- **Importer** (catalog column): fetch the field in `scripts/import/animethemes-client.ts` (respect
  the limits in data-sources.md), map it in `scripts/import/upsert.ts`, and add the field name to
  its `updateFromExcluded([...])` list — **otherwise re-imports never update it**. Cover it in
  `upsert.integration.test.ts`. Existing rows get the value on the next import run; tell the user.
- **Queries and server functions** in `src/features/*/` that should read or write the column.
- **Test fixtures**: `tests/fixtures/catalog.ts` (upstream shape) and `tests/fixtures/seed.ts`
  (our tables) — a new `NOT NULL` column breaks every seed until they set it.
- **Demo seed**: `scripts/dev/seed-demo.ts`, if the column is something the UI shows.
- **Deleting a user** must still cascade: a new table with a `user_id` gets
  `onDelete: 'cascade'` (architecture.md "Data model").

## 5. Verify

```bash
bun run typecheck && bun run check && bun run test
```

`bun run test` runs the integration suite against a migrated `noskip_test`, so a migration that
doesn't apply fails here. If the UI changed, also `bun run e2e`.

## 6. Docs, same change

- `docs/agents/architecture.md` — "Data model" diagram/bullets, "Layout" for a new schema file.
- `docs/agents/features-index.md` — new server functions.
- A non-obvious modeling choice → the `record-decision` skill.
- A new upstream field or source → `docs/agents/data-sources.md`.
- `docs/TODO.md` — close or add items.

Then show the user the migration SQL in a few lines (what it creates/alters/drops) and suggest one
commit title, e.g. `feat: store the season each theme aired in`.
